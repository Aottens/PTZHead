Create TEST-CHECKLIST.md with 7 test stages, each mapping to one or more Phase 4 success criteria (labeled SC-1 through SC-7). Structure:

**Header:** Title, date, prerequisites (hardware needed: ESP32, stepper drivers, motors, StreamDeck, router with power switch, computer with PlatformIO and Companion).

**Stage 1: Flash and Boot (SC-1)**
- Command: `pio run --target upload`
- Command: `pio device monitor` (115200 baud)
- Expected boot log lines (copy exactly from 04-RESEARCH.md "Expected Serial Log on Successful Boot" section):
  ```
  [I] BOOT: PTZHead starting
  [I] MOTION: 3-axis FastAccelStepper initialized
  [I] MOTION: preset=1 maxSps pan=2400 tilt=2400 zoom=2400
  [I] WIFI: Trying stored credentials
  ...
  [I] BOOT: Setup complete
  ```
- First boot note: captive portal expected if WiFi credentials were lost in framework switch (Pitfall 4 from research). Re-provision via portal -- this is expected, not a bug.
- Pass criteria checkbox: `[ ] Firmware uploads without error`, `[ ] Serial monitor shows "Setup complete"`, `[ ] WiFi connected (or captive portal completed)`

**Stage 2: Serial Motor Test (SC-2)**
Tests motor direction, speed scaling, decel, auto-disable. Serial-first isolates motor issues from network.
- Test commands and expected behavior (one checkbox per test):
  - `PAN 1.0` -- pan motor runs in positive direction. If direction is wrong, note: flip `kInvertPan` in ptz_config.h (currently `true`, change to `false` or vice versa)
  - `PAN -1.0` -- pan motor runs in opposite direction
  - `PAN 0.5` -- pan motor runs at roughly half speed
  - `STOP` -- pan decelerates smoothly to stop (not instant)
  - Wait ~500ms after stop -- motor shaft should be free to turn (auto-disable). If it stays locked too long or releases too fast, note the `setDelayToDisable(500)` value needs adjustment.
  - `TILT 1.0` / `TILT -1.0` / `STOP` -- same checks for tilt
  - `ZOOM 1.0` / `ZOOM -1.0` / `STOP` -- same checks for zoom
- If motors don't move at all: check enable pin polarity. Current config uses `setEnablePin(pin, true)` (active-low). If driver uses active-high, this needs flipping. See Pitfall 2 from research.
- Pass criteria checkboxes: `[ ] All 3 axes move`, `[ ] Direction correct (or noted for fix)`, `[ ] Speed scales with norm value`, `[ ] Smooth deceleration on STOP`, `[ ] Auto-disable ~500ms after stop`

**Stage 3: OSC Motion via Companion (SC-3)**
- Setup: Configure Companion generic-osc connection to ESP32 IP (from serial log) on port 8000, UDP protocol
- Alternative: use `ptzhead.local:8000` if mDNS works (tested in Stage 5)
- Test: Send `/ptz/pan` with value `1.0` from Companion button -- motor should respond
- Test: Send `/ptz/tilt` with value `1.0` -- motor responds
- Test: Send `/ptz/zoom` with value `0.5` -- motor responds
- Test: Send `/ptz/stop` -- all axes stop
- Test: Send `/ptz/pan/stop` while tilt is moving -- only pan stops
- Latency check: Press button, motor responds immediately (subjective <50ms feel test per user decision)
- Pass criteria: `[ ] OSC commands produce motor motion`, `[ ] Per-axis stop works`, `[ ] All-stop works`, `[ ] Latency feels instant (<50ms subjective)`

**Stage 4: Speed Presets (SC-3 continued)**
- Test: Send `/ptz/speed/preset` with value `0` (slow), then `/ptz/pan 1.0` -- motor moves slowly
- Test: Send `/ptz/speed/preset` with value `2` (fast), then `/ptz/pan 1.0` -- motor moves noticeably faster
- Test: Send `/ptz/speed/preset` with value `1` (medium) -- back to default
- Test: Change preset, send multiple motion commands -- preset persists until changed
- Pass criteria: `[ ] 3 distinct speed levels observable`, `[ ] Preset persists across commands`

**Stage 5: Feedback Verification (SC-4)**
- Prerequisite: Companion generic-osc connection active from Stage 3
- Test: Move pan axis -- Companion variable for `/ptz/status/pan/moving` shows `1`
- Test: Stop pan axis -- variable shows `0`
- Test: Repeat for tilt and zoom
- Test: Change speed preset -- `/ptz/status/preset` variable updates to new value
- Test: Observe `/ptz/status/rssi` -- shows negative dBm integer value (e.g., -55)
- Test: Wait 5+ seconds with no motion -- periodic snapshot still emits (1s interval). RSSI should keep updating.
- Handoff item: Verify feedback latency is within one loop tick (effectively instant)
- Handoff item: Verify RSSI emits at ~1s cadence
- Pass criteria: `[ ] Per-axis moving state updates correctly`, `[ ] Preset feedback works`, `[ ] RSSI shows valid negative dBm`, `[ ] All values are integers (no floats)`

**Stage 6: mDNS Discovery (SC-6)**
- From another device on the same network:
  - macOS: `dns-sd -B _osc._udp` (should show PTZHead instance)
  - macOS: `ping ptzhead.local` (should resolve to ESP32 IP)
  - Linux: `avahi-browse -r _osc._udp` or `ping ptzhead.local`
- Test: Wait 5 minutes, ping again (verifies GOT_IP restart pattern prevents the 2-minute mDNS silence bug)
- Pass criteria: `[ ] ptzhead.local resolves`, `[ ] _osc._udp service discoverable`, `[ ] Still resolves after 5 minutes`

**Stage 7: WiFi Resilience (SC-5)**
- Test A (idle): Power cycle router while motors are stopped. Observe serial log for disconnect/reconnect messages. ESP32 should reconnect automatically.
- Test B (moving): Start a motor via OSC, then power cycle router. Observe: heartbeat watchdog should stop motors within 500ms of lost connectivity. After router comes back, ESP32 should reconnect.
- Test: After reconnect, verify mDNS re-advertises (ping ptzhead.local again)
- Pass criteria: `[ ] Auto-reconnect after router power cycle`, `[ ] Motors auto-stop within ~500ms on network loss`, `[ ] mDNS works again after reconnect`

**Stage 8: Heap Stability (optional, Claude's discretion)**
- Note free heap value from serial log at boot (HEAP log line, every 60s)
- Run active session for 15-30 minutes (send OSC commands, change presets, observe feedback)
- Note free heap after 15min and 30min
- Pass criteria: `[ ] Heap stable (no significant downward trend)`

**Footer:** Summary table mapping SC-1 through SC-7 to stages. Space for notes on fixes applied.
