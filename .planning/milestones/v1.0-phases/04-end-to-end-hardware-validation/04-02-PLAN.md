Based on user's test results, apply fixes for any failing stages:

**If OSC commands don't produce motion (Stage 3):**
- Check serial log for OSC parse errors -- may indicate CNMAT library issue
- Verify Companion is sending to correct IP and port 8000
- Check if `g_osc.update()` is being called in main loop (it is -- verify serial log shows heartbeat/OSC activity)

**If feedback doesn't arrive at Companion (Stage 5):**
- This is Pitfall 7 from research. Check that Companion's generic-osc is listening on the port the firmware is sending to.
- The firmware sends to `remoteIP():remotePort()` of the last received packet. This should match Companion's listening port.
- If Companion variables aren't updating: check Companion's log for incoming OSC messages
- Potential fix: if reply port is wrong, may need to add a configurable feedback port to ptz_config.h

**If mDNS doesn't resolve (Stage 6):**
- Check serial log for "[I] MDNS: advertising ptzhead.local" message
- If missing: check that GOT_IP event handler is firing (look for the log line)
- If resolves initially but stops after 2 min: the end()-before-begin() pattern in GOT_IP may not be wired. Check ptz_wifi.cpp event handler.

**If WiFi doesn't reconnect (Stage 7):**
- Check serial log for DISCONNECTED event
- Verify `WiFi.reconnect()` is being called in the disconnect event handler
- Check if `WiFi.setSleep(false)` is called after reconnect (WIFI_PS_NONE)

**If heartbeat doesn't auto-stop (Stage 7):**
- Check that `g_motion.isMoving()` returns true while motor is running
- Check that `g_osc.lastRxMs()` is updating on each received packet
- Verify `kHeartbeatTimeoutMs = 500` in ptz_config.h

**If heap is declining (Stage 8):**
- Check that `msg.empty()` is called after every `OSCMessage.send()` in ptz_osc.cpp
- Look for any code path that creates an OSCMessage without emptying it

After any fix: `pio run --target upload` to re-flash, then re-test the affected stage.
